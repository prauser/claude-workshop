Spec → Impl → Review 워크플로우 온보딩

AI가 계획·구현·리뷰를 분담하고, 사람이 매 Gate에서 결정을 잠근다.

1. 왜 이 워크플로우인가

LLM에게 큰 작업을 한 번에 시키면 흔히 발생하는 문제 셋에 각각 답한다.

문제답어떻게 구현되어 있나
가정이 굳기 전 코드가 써짐계획·구현 분리/spec-plan 종료 후 사용자 확인 → /impl 시작
같은 컨텍스트의 자기검증 편향역할별 에이전트 분리implementer / reviewer / integrator 각자 다른 컨텍스트
사라지는 결정·근거artifact로 고정plan.md / task-N.md / result.md / manifest.yaml
흐름은 빠르게, 결정은 명시적으로.

2. 전체 흐름

/spec-plan {TICKET 또는 자유 프롬프트}
     │
     ├─ Step 0   read-only 에이전트 5개 병렬 (Jira / Spec / Code / Context / Test)
     ├─ Gate 1   Requirements          ← 사용자 OK 없이 통과 불가
     ├─ Gate 2   Plan + Ambiguities    ← 모든 Ambiguity 해소 전 통과 불가
     ├─ Gate 3   Test Strategy         ← 사용자 OK 없이 통과 불가
     ├─ Cross-review (3 rounds max)
     ├─ Final Review (사용자 최종 OK)
     └─ plan.md 저장 → 종료
                  │
                  ▼
/impl {TICKET}
     │
     ├─ plan.md 로드 → task-N-*.md 생성 (자기완결 task 파일)
     ├─ 작업 브랜치 자동 분기 (feat/{TICKET}-{slug})
     ├─ 각 task 순차 실행:
     │     preamble prepend → implementer → reviewer
     │                            │
     │                            └─ approved          → 다음 task
     │                            └─ needs-fix (p1/p2) → 핑퐁 (max 3 round)
     │     orchestrator가 code commit + artifact commit
     ├─ 모든 task 완료 → integrator (integration tests + quality gates)
     └─ 최종 보고 → 사용자 수동 push / PR

산출물

단계결과물위치
/spec-planplan.md (user_prompt 원문 포함).claude/plans/{TICKET}/
task 생성task-N-{name}.md.claude/tasks/pending/
role 결과*-result.md.claude/tasks/done/ (실패는 failed/)
integratormanifest.yaml, diff.patch, test-output.log.claude/runs/{TICKET}/

3. /spec-plan — 계획 모드

계획만. 코드 작성·구현 트리거 일체 금지. 모든 서브에이전트는 read-only.

사용법

/spec-plan OVDR-1234
/spec-plan OVDR-1234 우리 결제 모듈에 idempotency key를 도입하려고 해

호출 시 텍스트가 비어 있으면 한 번 물어본다. 이 원문은 plan.md frontmatter와 이후 모든 task 파일 상단에 그대로 복사 보존됨. 요약·정제 금지.

Step 0 — Context Gathering (병렬 5개)

에이전트모델역할
Jirasonnet티켓 정보 (jira-tools get)
Specsonnetdocs_path yaml 또는 PRD/specs/policies 평문
Codeopus코드베이스 임팩트 / 의존성 / 리스크
Contextsonnetlog_repo 과거 유사 작업 로그
Testsonnettest-engineer Strategy 모드 → <test-plan>

프로젝트에 ## Implementation Config가 없으면 Spec / Context Agent는 생략.

3-Gate 구조

각 Gate마다 사용자가 명시적으로 잠근다. "진행해" 한마디는 OK지만, 침묵은 승인이 아니다.

Gate출력통과 조건
1. RequirementsP0/P1 + Intentional Exclusions(비용·위험·타이밍 근거 필수) + Open Questions사용자 "OK"
2. Plan + AmbiguitiesImpact Scope + Task Breakdown(XS~XL) + Risks + Ambiguities모든 Ambiguity 명시 결정
3. Test StrategyUnit/Integration/E2E + Quality Gates사용자 "OK"
Open Questions vs Ambiguities — 혼동 주의.
Open Questions는 "구현 중 결정 가능". Ambiguities는 "지금 결정 안 하면 task 분해가 무너짐".

"건너뛰기" / "skip gates" 명시 시 세 Gate를 한 출력으로 합칠 수 있음. 기본은 분리.

Cross-review (3 rounds max)

충돌 유형 A~D (Code↔Spec, Code↔Tests, Jira↔Code, Test↔Code)를 자동 검출 → 해당 에이전트 재호출. 3회 후에도 미해결이면 Final Review에 양쪽 의견 그대로 노출.

Final Review

통합 요약. 사용자 선택: Revise / Investigate more / OK / Cancel. OK 시 plan.md 저장 후 종료. /impl을 자동 트리거하지 않는다 (의도된 분리).

4. /impl — 구현 모드

오케스트레이터. 직접 코드를 쓰지 않는다. 모든 작업은 서브에이전트 위임.

사용법

/impl OVDR-1234              # plan.md 로드 후 실행
/impl 로그 포맷 통일하고 싶어   # 자유 텍스트 — spec 토론으로 fallback
/impl                        # 무인자

티켓이 없으면 LOCAL-{YYYYMMDD-HHMMSS} 자동 부여.

활성화 시 자동 수행

  1. .claude/runs/{TICKET}, .claude/tasks/{pending,done,failed} 생성.
  2. 브랜치 정책: 현재가 master/main/develop이면 feat/{TICKET}-{slug}로 자동 분기. dirty면 멈추고 묻는다.

Task 파일의 5가지 필수 요소

  1. 자기완결성 — implementer가 대화 컨텍스트 없이도 단독 실행 가능.
  2. 사용자 원문 복사 — plan.md의 user_prompt를 그대로.
  3. AC = 실행 가능 bash — zero exit = pass. 추상 서술 금지.
  4. 주의사항은 X-Y 형식 — "X 하지 마라. 이유: Y". 이유 누락 시 무효.
  5. On completion — result 경로 + schema 링크 명시.

Implementer → Reviewer 핑퐁

preamble(7 rules) + task → implementer (slice-by-slice TDD)
                              │
                              ▼
                         result 파일 작성
                              │
                              ▼
                          reviewer 호출
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
     approved             needs-fix             [p3]/[p4] only
        │              (p1 or p2 있음)               │
        │                     │                     ▼
        │                     ▼            approved + follow-up TODO
        │            implementer 재호출
        │             (p1/p2만 전달)
        │                     │
        │                     ▼ (Round 2/3, max 3)
        │              여전히 미해결 → 사용자 escalate
        ▼
  orchestrator commit (코드 / artifact 2단)

Priority 라우팅

코드의미동작
p1차단성 (보안/데이터 손실/계약 위반)무조건 핑퐁
p2중요 (버그/커버리지/스펙 미스매치)사용자 defer 안 하면 핑퐁
p3사소 (스타일/네이밍)비차단 — handoff TODO
p4nit/제안비차단

핑퐁 비용 통제를 위해 p3/p4는 implementer에 전달하지 않는다. reviewer가 보이지 않는 무한 nitpick으로 빠지지 않도록 설계됨.

Commit 정책

reviewer approved 직후 orchestrator가 2단 커밋:

  1. 코드 커밋 — task ## Outputs 선언 경로만 git add. 와일드카드 금지 (secret 보호).
  2. 아티팩트 커밋 — .claude/tasks/done/ + .claude/runs/{TICKET}/.

자동 push / PR 생성은 하지 않음 — 사용자 수동.

Integrator

모든 task 완료 후 호출. integration test + Quality Gates 평가 + manifest.yaml 작성. 모든 gate가 pass여야 overall = success.

Runner 옵션 (선택)

기본 in-session. 비용·품질 trade-off:

/impl OVDR-1234 --preset cost-optimized
   → implementer만 headless-codex, reviewer/integrator는 in-session

처음에는 기본값 그대로 권장.

5. 사람이 개입하는 페이즈 — 체크리스트

이 워크플로우는 사람이 게이트를 지키지 않으면 가치가 절반이다.

Gate 1 — Requirements ★ 가장 중요

  • P0/P1 경계가 합리적? "전부 P0"은 의심.
  • Intentional Exclusions 이유가 동어반복은 아닌가?
  • 도메인 관점에서 누락된 P0는 없는가?
  • Open Questions가 정말 구현 중 결정 가능한가?

피드백: "수정" · "P0 X를 Exclusion으로" · "OK"

Gate 2 — Plan + Ambiguities

  • Task 사이즈 분포가 합리적? (모두 XL = 분해 부족)
  • 의존성 순서가 정확?
  • Ambiguities를 모두 결정했는가?
  • Impact Scope의 파일 리스트가 실제와 일치?

Gate 3 — Test Strategy

  • Risk areas가 실제 위험과 매칭?
  • Quality Gates가 측정 가능한 형태?
  • 수동 테스트 필요 부분 별도 메모

Final Review

  • 전체 그림에서 모순 없는가?
  • user_prompt가 실제 의도와 일치하는가?

/impl 중 — reviewer 결과

p1이 3 round 끝에도 남음plan.md 보강 필요
p2 deferrable"p2 X는 defer" 명시
p3/p4follow-up TODO로 충분
Chesterton's Fence 질문코드 의도 답변 필수

/impl 중 — task 실패

  • AC가 실현 불가능했나? → task 수정 후 pending 복귀
  • 외부 의존성? → 워크플로우 밖에서 해결
  • plan.md 가정이 틀렸나? → /spec-plan 재실행 (가장 흔함)

Integrator 보고 직후

  • Quality Gates 모든 항목 실제 통과 확인 (LLM 평가 검증)
  • manifest.yaml의 runner/model 확인 (사후 비교용)
  • 수동 테스트 (UI, 외부 시스템)
  • PR 전 diff 한번 더 훑기

PR 단계

  • PR 본문에 plan.md + ticket 링크
  • reviewer <handoff> TODO를 issue로 옮기기

6. FAQ

/spec-plan 없이 바로 /impl 써도 되나?

가능 (자유 텍스트 모드). 단 task 분해 품질이 떨어지고 reviewer 핑퐁이 늘어남. 첫 도입 1~2주는 무조건 /spec-plan 거치는 걸 권장.

plan을 수정하고 싶다.

/spec-plan {TICKET} 재호출하면 plan-v2.md로 저장됨. 활성 revision은 manifest.yaml에 기록.

reviewer가 너무 깐깐하다.

p1/p2가 진짜 필요한지 case-by-case로 판단. [p2] X는 defer 명시하면 통과. 반복되면 claude-config/agents/reviewer.md의 priority 정의를 팀 컨벤션에 맞게 조정.

어떤 작업에는 안 맞나?
  • 단순 hot-fix / 1-line 변경 — overhead가 더 큼. 그냥 수정 후 commit.
  • 탐색적 디버깅 — /impl의 analyzer/debugger 경로 또는 일반 대화.
  • UI 폴리싱 / 디자인 iteration — visual 피드백이 우선. overkill.
templates/workflow-contract/는 뭔가?

모든 artifact 형식의 SSOT. 새 runner를 추가해도 이 contract만 따르면 동일 audit 가능. contract.md부터 읽으면 됨.

8. 첫 시도 권장 시나리오

  1. 작은 티켓 (XS~M 한 개)로 시작. 거대 epic은 피하기.
  2. /spec-plan {TICKET} → 3 Gate 모두 분리해서 경험.
  3. 각 Gate에서 일부러 "수정" 한 번씩 — 피드백 루프 체감.
  4. /impl {TICKET} → 첫 task에서 reviewer 핑퐁을 한 번 보기.
  5. 끝나면 manifest.yaml · plan.md · task/result 파일을 천천히 다시 읽기 — artifact가 어떻게 추적 가능성을 만드는지가 진짜 가치.

개선 아이디어는 notes/impl-workflow/future-ideas.md에 적어두면 다음 iteration에 반영.
