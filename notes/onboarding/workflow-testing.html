워크플로우 테스트 & 피드백

실제로 돌려보고 게이트를 지키는 법

첫 시도 권장 시나리오

처음 워크플로우를 시험해 본다면 다음 순서로. 각 스텝은 다음을 학습하기 위해 설계되어 있다.

1

작은 티켓으로 시작

XS~M 한 개 규모로. 거대 epic은 피하기 — 첫 시도에서 워크플로우의 형태를 느끼는 게 목적이지, 실제 큰 작업을 끝내는 게 아니다.

2

/spec-plan {TICKET} 호출 — 3 Gate 모두 분리해서 경험

"건너뛰기"를 쓰지 말 것. 각 Gate가 어떤 정보를 만들어내는지 분리해서 봐야 의도가 보인다.

3

각 Gate에서 일부러 "수정" 한 번씩

피드백 루프 체감용. "OK" 한 번에 통과시키지 말고, 하나 정도 수정 지시를 줘서 어떻게 반영되는지 본다.

4

/impl {TICKET} — 첫 task에서 reviewer 핑퐁 한 번 보기

의도적으로 작은 결함을 두는 것도 학습 효과. p1/p2 라우팅이 실제로 어떻게 되는지 직접 보면 priority 체계가 와닿는다.

5

완료 후 artifact를 천천히 다시 읽기

.claude/runs/{TICKET}/manifest.yaml · plan.md · 각 task-N-*.md · *-result.md. artifact가 어떻게 결정의 추적 가능성을 만드는지 — 이게 이 워크플로우의 진짜 가치.

개선 아이디어는 기록 — 문제 발견·개선 아이디어는 notes/impl-workflow/future-ideas.md에 적어두면 다음 iteration에 반영.

사람이 개입하는 페이즈 — 체크리스트

이 워크플로우는 사람이 게이트를 지키지 않으면 가치가 절반이다. 어느 페이즈에서 무엇을 확인할지 미리.

시나리오를 선택하면 그 페이즈에서 확인할 항목만 보입니다. 체크 상태는 브라우저에 저장됩니다.

자주 묻는 질문 (FAQ)

/spec-plan 없이 바로 /impl 써도 되나?

가능 (자유 텍스트 모드). 단 task 분해 품질이 떨어지고 reviewer 핑퐁이 늘어남. 첫 도입 1~2주는 무조건 /spec-plan 거치는 걸 권장.

Plan을 수정하고 싶다.

/spec-plan {TICKET} 재호출하면 plan-v2.md로 저장됨. 활성 revision은 manifest.yaml에 기록.

Reviewer가 너무 깐깐하다.

p1/p2가 진짜 필요한지 case-by-case로 판단. [p2] X는 defer 라고 명시하면 통과. 패턴이 반복되면 claude-config/agents/reviewer.md의 priority 정의를 팀 컨벤션에 맞게 조정.

어떤 작업에는 안 맞나?
  • 단순 hot-fix / 1-line 변경 — overhead가 더 큼. 그냥 수정 후 commit.
  • 탐색적 디버깅 — /impl의 analyzer / debugger 경로를 쓰거나, 그냥 일반 대화로.
  • UI 폴리싱 / 디자인 iteration — visual 피드백 루프가 우선. /spec-plan overkill.
templates/workflow-contract/ 파일들은 뭔가?

모든 artifact 형식의 SSOT (Single Source of Truth). 새 runner를 추가해도 이 contract만 따르면 동일한 audit이 가능. contract.md부터 읽으면 됨.

Open Questions와 Ambiguities는 무엇이 다른가?
  • Open Questions — "구현 중에 결정해도 됨". Gate 1에 노출되지만 통과 막지 않음.
  • Ambiguities — "지금 결정 안 하면 task 분해가 무너짐". 모든 항목 해소 전 Gate 2 통과 불가.
Runner 옵션은 언제 바꾸나?

처음에는 기본값(in-session) 그대로. 비용이 부담되거나 큰 batch를 돌릴 때 --preset cost-optimized로 implementer만 headless-codex로 빼는 것이 일반적. 품질 차이를 체감하려면 같은 task를 두 번 돌려 manifest.yaml의 runner/model 필드를 비교해 보면 됨.

커밋이 자동으로 push되지 않는다.

의도된 설계. orchestrator는 로컬 커밋만 만들고 push·PR 생성은 사용자가 수동으로. 마지막 사람 확인 기회를 보장하기 위해서.

개념·구조 설명은 workflow-concepts.html 로.
