# Workflow Observability & Agent Audit Proposal

> Status: draft for review  
> Scope: Claude Code `/spec-plan` and `/impl` workflows first; provider-neutral extension later  
> Date: 2026-04-25  
> Phase 0 note: `codex-parity-runner-strategy.md` takes priority for the next implementation step. For Phase 0, use only artifact-only audit checks from this proposal. Defer broad decision records, normalized low-level `events.jsonl`, transcript-heavy LLM audit, and hard gates until the artifact contract and one Codex runner validation are complete.

## Summary

This proposal adds an observability and audit layer to the existing Claude Code workflow.

The goal is not to recover or depend on raw model chain-of-thought. The goal is to make agent behavior auditable by combining:

1. Raw execution traces already produced by Claude Code.
2. Explicit, short decision records written by agents at meaningful decision points.
3. Normalized event logs generated by hooks or post-processing scripts.
4. Post-run evaluation that detects missing evidence, unsupported decisions, scope drift, and workflow deviations.

This works for the current Claude-native `/spec-plan` and `/impl` flow, and it can later support Codex or other runners by normalizing their logs into the same event schema.

## Why This Is Needed

The current workflow already has useful structure:

```text
/spec-plan TICKET
  -> gather Jira/spec/code/context/test information
  -> create plan.md
  -> user approval

/impl TICKET
  -> read plan.md
  -> create task files
  -> implementer
  -> reviewer
  -> fix loop
  -> integrator
  -> final report
```

Claude Code also leaves raw session logs and hook inputs, including tool calls, tool inputs, tool outputs, subagent activity, transcript paths, and final assistant messages.

However, raw logs alone have three problems:

1. They are rich but hard to compare across runs.
2. Important decision points may be implicit in long transcripts.
3. Model thinking output is not a stable or portable primary data source.

So the system needs a light but explicit audit layer.

## Important Constraint: Do Not Depend On Raw Thinking

Raw thinking or chain-of-thought should not be treated as the primary analysis target.

Reasons:

- Visibility depends on model, version, product surface, and configuration.
- Some systems return summarized thinking, omitted thinking, encrypted reasoning items, or only usage counts.
- Summaries are useful hints but are not guaranteed to be the full internal reasoning process.
- Asking agents to output long thinking can increase cost, latency, and noise.
- Cross-provider comparison becomes unstable if one provider exposes more thinking text than another.

The stable analysis target should be:

```text
tool trace + file diff + test/build output + explicit decision record + final result
```

Thinking text, when present, should be treated as optional supporting context.

## Design Principle

The audit system should not trust any single source.

```text
Raw tool trace:
  What actually happened.

Decision record:
  What the agent claims it decided and why.

Evaluator:
  Checks whether the claim is supported by the trace.
```

This makes decision records useful without treating them as ground truth.

## Proposed Data Layers

### Layer 1: Raw Logs

Preserve the original logs as much as possible.

Examples:

```text
.claude/projects/.../{session-id}.jsonl
.claude/tasks/pending/*.md
.claude/tasks/done/*-result.md
.claude/tasks/failed/*.md
hook input JSON
tool stdout/stderr
git diff snapshots
test/build logs
```

Raw logs are the primary evidence store. They should be immutable once archived.

### Layer 2: Explicit Decision Records

Agents should write short records only at meaningful decision points.

Do not record every search or file read. Record decisions that affect scope, design, testing, or recovery.

Recommended template:

```markdown
## Decision Record

Decision:
Evidence:
- {file/tool/log reference}
Alternatives considered:
Assumptions:
Uncertainty: low | medium | high
Validation:
Next step:
```

Good example:

```markdown
## Decision Record

Decision: Implement validation in the parser boundary instead of the UI caller.
Evidence:
- Read src/parser.ts
- Read src/ui/form.ts
- rg showed parseInput is also used by batch import
Alternatives considered:
- UI-only validation, rejected because batch import would bypass it.
Assumptions:
- parseInput remains the shared boundary.
Uncertainty: medium
Validation:
- Add parser unit tests for invalid input.
- Run existing form tests.
Next step:
- Modify parser and add tests.
```

Bad example:

```markdown
I considered the architecture and this is the best approach.
```

The evaluator must be able to verify the evidence against actual tool traces.

### Layer 3: Normalized Events

Create a compact `events.jsonl` from raw logs and hooks.

Example:

```json
{"event":"workflow_started","workflow":"impl","ticket":"OVDR-1234","runner":"claude-code"}
{"event":"agent_started","role":"implementer","task":"task-1"}
{"event":"tool_call","role":"implementer","tool":"Read","path":"src/parser.ts"}
{"event":"tool_call","role":"implementer","tool":"Bash","command":"npm test -- parser"}
{"event":"test_result","passed":12,"failed":1}
{"event":"decision_recorded","role":"implementer","task":"task-1","uncertainty":"medium"}
{"event":"review_result","status":"needs-fix","important":2}
{"event":"retry_started","task":"task-1","round":2,"reason":"review_needs_fix"}
{"event":"workflow_finished","status":"success"}
```

The normalized layer enables metrics and cross-run comparison without losing access to raw evidence.

### Layer 4: Evaluation Report

After each workflow run, an evaluator agent reads:

- Raw transcript.
- Tool trace.
- Task/result files.
- Decision records.
- Diff and test logs.
- Normalized events.

It writes:

```text
.claude/runs/{run-id}/audit.md
.claude/runs/{run-id}/metrics.json
.claude/runs/{run-id}/deviations.json
.claude/runs/{run-id}/retro.md
```

## What To Record

### Always Automatic

These should be captured by hooks, transcript post-processing, or wrapper scripts:

- User prompt.
- Workflow name and ticket.
- Agent role.
- Tool calls.
- Tool inputs and outputs where safe.
- File paths read or modified.
- Diffs.
- Command exit codes.
- stdout/stderr summaries.
- Test/build results.
- Review status.
- Retry counts.
- Start/end timestamps.

### Agent-Written Decision Records

Require records for:

- Task decomposition choices.
- File/module ownership choices.
- Implementation approach.
- Test strategy.
- Debugging root-cause hypothesis.
- Any failed command followed by continued work.
- Any test failure followed by code edits.
- Any review issue accepted, deferred, or rejected.
- Any scope expansion beyond the task file.
- Any dependency/config/build/CI change.
- Any high-uncertainty assumption.

Avoid requiring records for:

- Simple file reads.
- Repeated searches for the same hypothesis.
- Routine test runs.
- Mechanical formatting.

## Missing Decision Detection

Decision records will be incomplete if we rely only on agent discipline. The evaluator must detect missing records.

Suggested rules:

```text
Flag missing_decision when:
- changed_files >= 3 and no implementation decision record exists
- changed_lines >= 100 and no design/scope record exists
- package/build/CI/config files changed and no tradeoff record exists
- tests failed and code changed afterward without a failure interpretation record
- review returned needs-fix and code changed afterward without a fix rationale
- actual diff includes files outside task Outputs without scope-expansion record
- agent used words like "assume", "probably", "seems", "not sure" without uncertainty record
- workflow completed without tests and no explicit test deferral record exists
```

Example normalized event:

```json
{
  "event": "missing_decision",
  "kind": "scope_expansion",
  "severity": "important",
  "evidence": "task allowed src/parser.ts, diff also modified src/importer.ts"
}
```

## Evaluator Checks

The evaluator should not merely summarize. It should audit.

Core checks:

```text
1. Evidence support
   - Does each Decision Record cite files/tools that were actually read or run?

2. Scope control
   - Did modified files match the task Outputs section?

3. Verification
   - Were promised tests actually run?
   - Did failing tests get interpreted before code changes?

4. Review loop quality
   - Were reviewer issues addressed?
   - Did the same issue recur across rounds?

5. Context sufficiency
   - Did the agent modify code without reading nearby tests or call sites?

6. Workflow compliance
   - Did `/spec-plan` stay planning-only?
   - Did `/impl` create task files and result files?
   - Did integrator evaluate quality gates?

7. Recording quality
   - Are decision records specific, evidence-backed, and short?
   - Are there unsupported claims?
```

## Suggested File Layout

Keep existing `.claude/tasks` and `.claude/plans`, then add run-level audit output:

```text
.claude/
  plans/{TICKET}/plan.md
  tasks/
    pending/
    done/
    failed/
  runs/
    {run-id}/
      manifest.json
      events.jsonl
      metrics.json
      deviations.json
      audit.md
      retro.md
      raw/
        transcript.jsonl
        hook-events.jsonl
        test-output.log
        diff.patch
      decisions/
        task-1-implementer.md
        task-1-reviewer.md
```

For long-term learning logs, sync a compact version into `impl-logs`:

```text
impl-logs/{repo_name}/{TICKET}/
  plan.md
  steps/
  audit.md
  metrics.json
  deviations.json
  retro.md
```

## Hook Integration

Claude Code hooks can provide observability and soft gates.

Useful events:

- `UserPromptSubmit`: attach workflow context or validate prompt shape.
- `PreToolUse`: capture intended tool use and optionally block dangerous actions.
- `PostToolUse`: capture result, stdout/stderr, and add context.
- `Stop`: validate final response and required result files.
- `SubagentStop`: validate subagent output and decision records.
- `SessionEnd`: archive final logs.

Recommended rollout:

```text
Stage 1: Observe only
  - Capture raw hook events.
  - Do not block.
  - Generate audit.md after the run.

Stage 2: Soft gate
  - Warn on missing records or unsupported claims.
  - Add findings to final report.

Stage 3: Hard gate for critical issues only
  - Block completion if result file is missing.
  - Block completion if tests were promised but not run.
  - Block completion on unacknowledged scope expansion.

Stage 4: Policy tuning
  - Use recent audits to refine recording rules.
```

## Metrics

Start with simple metrics:

```json
{
  "workflow": "impl",
  "ticket": "OVDR-1234",
  "tasks_total": 3,
  "tasks_completed": 3,
  "review_rounds_total": 4,
  "missing_decisions": 2,
  "unsupported_decision_claims": 1,
  "scope_expansions": 1,
  "tests_promised": 3,
  "tests_run": 2,
  "failed_commands": 1,
  "retries": 1
}
```

Later metrics:

- Time per agent.
- Tool calls per task.
- Files read before edit.
- Tests run before/after edit.
- Review issue recurrence.
- Decision uncertainty vs actual failure rate.
- Prompt/agent version vs success rate.

## Claude-Only Use

This proposal does not require Codex or another provider.

For Claude Code only:

```text
Claude native slash command remains the orchestrator.
Claude native subagents remain the workers.
Claude hooks capture raw events.
Decision records are added to task/result output.
Evaluator agent audits the full run after completion.
```

This preserves the existing interactive workflow while improving observability.

## Provider-Neutral Extension

If Codex or another runner is added later, do not create a separate analysis model.

Instead:

```text
Claude transcript -> normalize -> events.jsonl
Codex jsonl       -> normalize -> events.jsonl
Other runner logs -> normalize -> events.jsonl
```

All providers should produce:

- Task input.
- Tool trace.
- Decision records.
- Result file.
- Test/build evidence.
- Normalized events.

Provider-specific raw logs remain available under `raw/`.

## Review Questions

For Claude-side review, focus on these questions:

1. Can Claude Code hooks reliably capture the required tool and transcript data?
2. Should decision records live in task result files, separate `decisions/` files, or both?
3. Which missing-decision rules should start as soft warnings?
4. Which conditions are severe enough to block `Stop` or `SubagentStop`?
5. How much decision-record burden is acceptable before implementation velocity drops?
6. Should the evaluator run automatically after every `/impl`, or only when requested?
7. Should audits be synced to `impl-logs` by default?

## Initial Implementation Plan

### Phase 1: Minimal Audit Layer

- Add a decision record section to implementer, reviewer, integrator outputs.
- Add a post-run parser that copies the Claude transcript into `.claude/runs/{run-id}/raw/`.
- Generate `events.jsonl` with basic workflow, agent, tool, test, and review events.
- Generate `audit.md` with missing result files, missing tests, and scope drift.

### Phase 2: Evaluator Agent

- Add an `audit-reviewer` or `workflow-auditor` agent.
- It reads raw logs plus normalized events.
- It outputs `audit.md`, `metrics.json`, `deviations.json`, and `retro.md`.

### Phase 3: Soft Gates

- Add `Stop` and `SubagentStop` hooks that warn on critical missing artifacts.
- Keep blocking disabled initially.
- Review false positives for several runs.

### Phase 4: Hard Gates For Critical Failures

- Block only objective failures:
  - Missing result file.
  - Invalid result schema.
  - Promised tests not run.
  - Scope expansion without note.

### Phase 5: Continuous Improvement

- Use recent audits to update:
  - command prompts,
  - agent prompts,
  - task templates,
  - decision-record requirements,
  - quality gates.

## Non-Goals

- Do not attempt to reconstruct private or hidden chain-of-thought.
- Do not require verbose reasoning before every tool call.
- Do not block workflow completion for every missing annotation.
- Do not treat agent-written decision records as ground truth.
- Do not force provider-specific logs into a lossy format; preserve raw logs separately.

## Core Recommendation

Keep the Claude-native workflow. Add an audit layer around it.

The most useful system is not one that exposes every thought. It is one that can answer:

```text
What did the agent do?
What evidence did it claim to use?
Is that evidence present in the trace?
Where did behavior diverge from the workflow spec?
What should change in the prompt, task template, hook, or quality gate?
```

That gives us practical workflow improvement without depending on unstable thinking visibility.
